opthub

PHASE 1 · DEMO SPEC

A CLI on every dev laptop, shipped with a sandboxed agent. It watches the LLM traffic your code actually makes and continuously proposes — or safely applies — optimizations that cut cost and latency without moving accuracy, leaking data, or losing work.

01

The problem is not finding optimizations

A team ships LLM features. Three months later the same five things are true of almost every codebase:

  • System prompts have accumulated dead instructions and stale few-shots nobody dares remove.
  • Every call goes to the biggest model, because that is what worked on day one.
  • Prompt caching was never configured, so the same 8k-token preamble is paid for on every request.
  • Tool schemas list thirty tools where the workload uses four.
  • Nobody knows the p95, the $/1k requests, or whether last week's prompt edit hurt accuracy.

Each of these is a known fix. None of them get done — because doing one means proving you did not break anything, and nobody has an eval harness handy at the moment they notice the problem.

The bet

Put the optimizer and the eval harness in the same loop, on the laptop, and make the gate non-optional.

02

Goals & non-goals

—GoalHow the demo measures it

G3Never regress latencyp95 ≤ baseline × 1.05
G4Never widen the security surfaceZero new findings; redaction verified at capture
G5Survive a crashkill -9 mid-run → opthub resume, no duplicate spend
G6Two autonomy modesPolicy decides auto-apply vs. PR, per optimizer tier

Out of scope for Phase 1

Server-side or production deployment — laptop only. Fleet aggregation across many devs. Non-LLM workloads such as builds, infrastructure, or SQL. Auto-merging pull requests: the agent opens, a human merges. Any form of training or fine-tuning.

03

Architecture: the agent is untrusted

This is the load-bearing decision. The agent that proposes optimizations can never write to your repo and never sees raw secrets. It produces a description of a change — a signed JSON proposal — and nothing else.

Agent sandbox

Docker · untrusted

  • Repo mounted read-only
  • No host credentials — short-lived scoped tokens, brokered
  • Network egress allowlist, DNS pinned
  • Output limited to a signed Proposal JSON
  • Crash blast radius: the container dies, the task resumes
Trust boundary

opthubd — host daemon

Unprivileged · the only writer

  • Capture proxy on 127.0.0.1:7777, redact-before-disk
  • Journal (SQLite WAL) + content-addressed artifact store
  • Apply engine — the only component that mutates anything
  • Re-runs every gate itself before writing; it does not trust the sandbox's claim that gates passed
  • Enforces the daily verification spend cap

Capture

The developer points their SDK at the local proxy — ANTHROPIC_BASE_URL=http://127.0.0.1:7777. The proxy forwards upstream unmodified and records. Redaction happens before anything touches disk: configured detectors replace matches with stable pseudonyms («email:a3f») so a trace stays semantically replayable without holding the real value. The reverse map lives in the host keychain and never enters the sandbox. Capture is opt-in per project, off by default, and opthub capture status always tells the truth about what is being recorded.

04

The gate

Every candidate must clear four independent gates. Any failure kills the candidate. There is no override flag in Phase 1 — that is deliberate.

Accuracy

Replay the golden set against the candidate and score with a two-part scorer. Deterministic checks run first because they are fast and free: JSON schema validity, required fields, tool-call name and arity match, refusal detection, and whatever regex assertions the developer declared. Only free-text outputs reach the LLM judge, which scores pairwise against the baseline output with position-swap to cancel order bias. The judge model is pinned in policy and is never one of the models being optimized to.

Latency

Replay measures wall-clock p50/p95/p99 per workload. Measured warm-cache for cache-related optimizers and cold for everything else, so caching cannot flatter an unrelated change.

Security

  • No redaction detector disabled or weakened
  • Target model in security.model_allowlist; data-residency tag matches policy
  • No new egress destination versus baseline
  • Workload not listed in never_downgrade
  • Prompt-injection surface: the candidate must not newly interpolate untrusted content into the system prompt, or newly grant a tool the baseline did not have

Economics — the optimizer must pay for itself

Verification costs real money. A candidate is only worth verifying if it earns back the verification: 

projected_30d_savings > verification_spend × policy.budgets.min_roi   // default 3×

opthub estimates verification cost before running it and skips candidates that cannot clear the bar. The daily cap is enforced in the daemon, not in the sandbox.

05

Optimizer tiers set the autonomy

Optimizers are tiered by how much they can possibly change model output. The tier — not a human's intuition about "risky" — determines the default autonomy.

T0

Token-identical · auto-apply

Cannot change the sampled distribution at all. This is where the free lunch lives — prompt caching alone typically explains most of the demo's cost drop, and it is provably output-preserving.

cache-primingtransport-tuning
T1

Output-affecting, eval-gated · auto-apply if policy allows

Changes the token stream but not which model answers. Auto-applies only when policy opts the specific optimizer in and the eval clears with n above threshold.

tool-schema-slimmingcontext-pruningprompt-compactionoutput-shaping
T2

Changes which model answers · always propose

Never auto-applies in Phase 1, regardless of how well it scores. A human sees the evidence and decides.

model-routingbatch-collapse
06

Policy

opthub.policy.yaml is committed to the repo and linted by opthub policy lint. It is the whole configuration surface — there is no second place where behavior is decided. 

version: 1

budgets:
  accuracy:  { min_score: 0.95, relative_drop_max: 0.00, min_samples: 30 }
  latency:   { p95_regression_max: 1.05 }
  cost:      { target_reduction: 0.30 }
  verify:    { daily_usd_cap: 5.00, min_roi: 3.0 }

security:
  redaction: [email, phone, api_key, jwt, pan]
  egress_allowlist: [api.anthropic.com]
  model_allowlist:
    - claude-opus-5
    - claude-sonnet-5
    - claude-haiku-4-5-20251001
  judge_model: claude-opus-5          # pinned; never a routing target
  data_residency: us
  never_downgrade:
    - supportbot/pii-extract

autonomy:
  default: propose
  auto_apply_tiers: [T0]
  auto_apply_optimizers:
    - tool-schema-slimming
  require_approval_optimizers:
    - model-routing
    - prompt-compaction
  apply_mode: pr                      # pr | worktree | direct
07

Journal & recovery

Everything opthub does is a task, and every task is a replayable event log. This is what makes "continuously optimizes" safe to leave running.

PENDING→ CAPTURING→ BASELINING→ OPTIMIZING→ VERIFYING→ PROPOSED→ APPLIED| REJECTED| ROLLED_BACK

Storage

  • .opthub/journal.db — SQLite in WAL mode. events(task_id, seq, ts, type, payload_cas, prev_hash), append-only and hash-chained, so tampering is detectable.
  • .opthub/cas/<sha256> — content-addressed store for traces, candidate configs, eval results, and diffs. Events reference artifacts by hash, so the log stays small and replay is exact.

Idempotent side effects

Every effect that costs money or touches the world is written as a triple:

INTENT(effect_id, description, cost_estimate)
    … perform …
EFFECT(effect_id, result_cas)
CONFIRM(effect_id)

On resume, any INTENT without a matching CONFIRM is checked against the provider by idempotency key before being retried. This is what makes kill -9 mid-verification safe: resume never re-pays for an eval run that already completed.

08

CLI surface

opthub init                          # scaffold .opthub/, policy, gitignore
opthub daemon start | stop | status

opthub capture start --port 7777     # begin recording
opthub capture status                # what is recorded, redaction on/off
opthub capture stop

opthub workloads list                # call sites + current cost/latency
opthub baseline create --workload W --from 24h --n 50
opthub baseline show W

opthub optimize [--workload W] [--tier T0,T1] [--dry-run]
opthub proposals list | show <id>
opthub proposals apply <id> [--as-pr]
opthub proposals reject <id> --reason "..."
opthub rollback <apply-id>

opthub report --since 7d             # the dashboard, in the terminal
opthub policy show | lint
opthub resume

09

The demo, act by act

Seeded repo: supportbot — a small support-ticket app with three workloads (classify, draft-reply, pii-extract) and a synthetic traffic replayer. Total running time about six minutes.

I90 sec

Observe

opthub daemon start → opthub capture start → replay 400 synthetic tickets. opthub workloads list shows three workloads with $/1k, p95, and a token breakdown. An 8k-token system preamble is visible on every draft-reply call — the audience spots the waste before opthub says a word. opthub baseline create --n 50 freezes the golden set.

II2 min

Optimize, and get told no

opthub optimize. The sandbox spins up, the agent reads traces read-only, and five candidates come back. The gates run live in the terminal:

CandidateTierAccuracyp95CostVerdict
cache-priming T0 tie (token-identical) −22% −31% Auto-applied
tool-schema-slimming T1 0.96 → 0.96 −4% −6% Auto-applied
context-pruning T1 0.96 → 0.96 −9% −8% Auto-applied
model-routing → Haiku T2 0.96 → 0.95 −41% −58% Needs approval
prompt-compaction (aggressive) T1 0.96 → 0.89 −11% −14% Rejected · accuracy
The moment

The rejection is the demo. A cheaper and faster candidate is thrown away because it lost seven accuracy points. Anyone can show a cost graph going down; showing the system refuse a tempting win is what makes the graph believable.

III60 sec

The pull request

opthub proposals apply model-routing --as-pr opens a PR carrying the diff, the evidence table, the golden-set delta, and per-example links back into the journal. A human reads it and merges on stage. The T2 tier did exactly what the policy promised: it did not decide for anyone.

IV60 sec

Crash and recover

Start a fresh optimize run. Mid-verification, kill -9 $(pgrep opthubd). Then opthub resume:

11

Risks

RiskMitigation
Golden set overfits — the gate passes but production regressesRotate a held-out slice each run and report the score on unseen traces separately from the gated score
Judge drift makes scores incomparable over timeJudge model pinned in policy; changing it forces a baseline re-freeze
Devs read the capture proxy as a MITM on their trafficOpt-in per project, off by default, local-only bind, truthful capture status, redact-before-disk, source published
Verification costs more than it savesROI gate (§04) plus a hard daily cap enforced in the daemon
Agent sandbox escapeRead-only mount, no host creds, egress allowlist, output limited to signed JSON — and the host re-runs every gate independently
"Continuous" turns into noiseProposals deduped by candidate hash; a rejected candidate is not re-proposed until its inputs change
