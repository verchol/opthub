The Optimization Playbook

Every lever you can pull to cut the cost, latency and token consumption of running LLM agents in production — organised by the layer it lives in, each with its knob, its likely win, and, stated honestly, its accuracy risk. Written to be run as experiments: every row here is something you can configure and measure, not admire.

How to read the win column. Figures are drawn from the cited sources and reflect their workloads, not a promise about yours — which is exactly why each is framed as an experiment. The one rule that survives every workload: an optimization that trades quality is only cheaper if the quality it costs you was quality you didn't need. Measure it, don't assume it.

Model layer
Model routing & tiering TRADES QUALITY

Knob: which model serves which request. Route well-defined or low-stakes work to a smaller/cheaper model; reserve the frontier model for hard reasoning and orchestration.

The single largest lever in most production accounts. Uber built evaluation benchmarks from real production work, plotted cost-per-completed-task against quality, and deployed whatever sat on the Pareto frontier — refreshing the choice every few weeks as the frontier moved. We reproduced the shape of this directly: on a spec-following coding task an open-weights model reached ~85–94% of frontier correctness at 84–92% lower cost; on a knowledge-recall task the same model fabricated facts and collapsed to ~27%. Routing is powerful and workload-specific in equal measure.

Sources: Uber, Efficient Software Factory · our own harness runs (regex 94%, landscape 27%)

Model layer
Quantization TRADES QUALITY

Knob: the numeric precision the weights and activations are served at. Lower precision = less memory and higher throughput, at some accuracy cost.

FormatWinAccuracyWhen
FP8~2× memorynear-lossless on Hopper/Ada; absorbs wide activation rangesthe recommended first try on modern GPUs
INT8 (weight-only)~2× memorynegligible perplexity change — "very safe"safe default fallback
INT8 SmoothQuant~2×+small loss; needs activation smoothingif FP8 unavailable
AWQ (4-bit)~4× memoryprotects the ~1% salient channels; holds reasoning best at 4-bitthe 2026 production default for 4-bit GPU serving
GPTQ (4-bit)~4× memorymore loss than AWQ on reasoningwhen AWQ kernels unavailable

Standard advice: FP8 first, drop to INT8 SmoothQuant, go to AWQ/GPTQ at 4-bit only when you need more than FP8's 2× saving. Weight-only INT8 is the free lunch; 4-bit is where reasoning quality starts to move.

Sources: VRLA Tech · AppScale · AWS SageMaker

Model layer
Distillation & domain fine-tuning TRADES QUALITY

Knob: replace a large general model with a small model adapted to your domain. Spotify is the cleanest published example: they took Llama variants at 1B–8B and adapted them with supervised fine-tuning, RLHF and DPO across 10 Spotify-specific tasks — reaching 4× user engagement on explained recommendations and a 14% task lift over baseline Llama, with minimal MMLU degradation ("no catastrophic forgetting"). Smaller fine-tuned models matched larger general ones on domain tasks "while offering better latency and cost."

The risk is narrowing: a model tuned for your 10 tasks may be worse everywhere else. Spotify guarded this by measuring MMLU throughout.

Source: Spotify via ZenML LLMOps DB

Serving layer
Serving engine — vLLM / SGLang LOSSLESS

Knob: which inference server runs the model. This is the most consequential lossless choice, and the one a per-team model comparison never sees. vLLM's PagedAttention partitions the KV cache into fixed blocks, eliminating fragmentation and enabling memory sharing. Spotify called adopting vLLM "a game-changer." SGLang's RadixAttention is the sibling technology. Everything below (batching, speculative decoding, prefix caching) is a feature of this layer — turn it on and the model's output is byte-identical.

Sources: Inside vLLM · vLLM

Serving layer
Continuous batching LOSSLESS

Knob: evict finished requests and insert new ones at every decoding step instead of batching statically. Reported up to 23× throughput with lower p50 latency versus static batching. Pure serving efficiency; identical output.

Source: vLLM continuous batching

Serving layer
Speculative decoding LOSSLESS

Knob: a small draft model proposes several tokens, the target model verifies them in one pass. Latency drops; output is provably identical to the target model because every token is verified. vLLM supports n-gram, suffix, EAGLE and similar drafters. Free latency — the only cost is the draft model's memory.

Source: vLLM speculative decoding

Serving layer
Prefix / KV caching LOSSLESS

Knob: reuse the KV cache for a shared prompt prefix so repeated context isn't recomputed. This is the mechanism behind "prompt caching" — but it lives in the serving stack, which is why the same open-weights model has a 0% or a 90% cache hit rate depending entirely on who serves it. We measured this: a frontier model on a caching endpoint reused 93–95% of its input at 0.1× price; the same-class open model on a non-caching endpoint reprocessed 1M+ tokens at full price every turn — enough to erode much of its per-token cost advantage over a long session.

Sources: vLLM APC · our own harness (baseline 93.7% hit vs open-model 0%)

Context layer
Prompt caching (TTL tuning) LOSSLESS

Knob: cache the stable prompt prefix and tune the TTL to the workload. Uber uses a 5-minute TTL for short-lived subagents and 1-hour for main threads (which have idle gaps): a 5-min write costs 1.25×, a 1-hour write 2×, but reads are 0.1×, so the longer TTL wins whenever the prefix is reused across an idle gap. Same output, lower bill.

Source: Uber

Context layer
Context compaction TRADES QUALITY

Knob: compress conversation history, tool outputs and files before they reach the model. Uber auto-compacts at 400K tokens despite larger windows, to bound cache-burst and repeated-input cost. A local compaction proxy (Headroom) claims 20% fewer tokens for coding agents and 60–95% for JSON. The risk is real and directional: compaction can drop the one detail the next step needed, and — we observed — it can lower the prompt-cache hit rate by disturbing the stable prefix, working against the very savings it delivers. Measure both cost and task success.

Sources: Uber · Headroom · our own harness (cache-hit drop under compaction)

Context layer
Tool-schema shaping LOSSLESS

Knob: how many tool definitions, and in what form, sit in the context. When an agent has dozens of tools, their JSON schemas can consume 40–50% of the window — raising cost and latency and causing "LLM confusion" from irrelevant documentation. Techniques, roughly in order of payoff:

TechniqueReported reduction
Code-execution mode98.7% (Anthropic) · 99.9% (Cloudflare: 2,500 endpoints → 2 tools)
Tool search / on-demand loading~85% (10K+ → ~3K tokens/request)
Progressive disclosure (categories → full schema)load the schema only when the tool is chosen
Schema dedup via JSON $refeliminate repeated sub-schemas across tools

Rule of thumb from the field: no more than 10–15 tools live at once. All lossless — the model's capability is unchanged, only what it must read shrinks.

Sources: The New Stack · StackOne · MCP SEP-1576 · MindStudio

Context layer
Reasoning effort TRADES QUALITY

Knob: how much the model is allowed to think. Output tokens bill at a multiple of input, so reasoning effort is a direct cost dial. Uber defaults to Medium, not maximum — the cost/quality knee for most work. Raise it only for the tasks that measurably need it.

Source: Uber

Orchestration layer
Turn & request reduction TRADES QUALITY

Knob: how many round trips the agent takes. Every turn resends the whole conversation, so cost grows roughly with the square of turns. Uber's cost model is explicit — Users × Sessions × Turns × Requests × Tokens × Price — and each factor is optimised in isolation. Fewer, better turns is usually the highest-leverage orchestration change; the risk is cutting a turn the task needed, which shows up as lower success, not lower cost.

Source: Uber

Orchestration layer
Subagent downgrade TRADES QUALITY

Knob: run well-scoped subtasks (review, extraction, triage) on a cheaper model while the flagship orchestrates. A special case of routing, applied inside a single session. We use it directly: a Sonnet reviewer gates a task an orchestrating model planned. Cheap where the subtask is bounded; risky where the subtask secretly needs the flagship's judgement.

Source: Uber · our own reviewer subagent

Orchestration layer
Code-mode batching LOSSLESS

Knob: collapse a sequence of tool calls into one script the agent writes and runs, instead of N model turns with intermediate polling. Uber reports 55–71% token reduction for small result sets and ~100% for large bulk workflows, by keeping polling loops out of the model's context entirely. The work is identical; only the round trips vanish.

Source: Uber

Measurement
Denominating cost by outcome

None of the above means anything measured in tokens alone. The metric that ties spend to value is cost per completed unit of work — Uber tracks cost per merged PR, per review posted, per alert triaged. We use cost-per-passing-test and cost-per-rubric-point. The reason is concrete: in our runs the cheapest model per token was often the most expensive per passing test, because it failed more. A price list ranks models the wrong way; an outcome denominator ranks them right.

The through-line. Lossless levers — serving engine, batching, speculative decoding, prefix caching, prompt caching, tool-schema shaping, code-mode — should simply be on; there is no quality to trade. The quality-trading levers — routing, quantization, distillation, compaction, effort, turn-cutting — are where the real decisions live, and none can be settled from a spec sheet. They interact (caching amortises the context that compaction shrinks; routing to a weak model raises turns): a change that helps one dimension can erode another. That interaction is the argument for owning optimization centrally, per workload, measured — not scattered across teams each pulling one knob blind.
