Anatomy of an experiment

An experiment is five things bound together: a prompt, a strategy built from rules, an original session that becomes the baseline, operational limits, and a verifier. Bind them and you get two runs that are identical except for one parameter — which is the only arrangement in which the answer means anything.

Part 1

Prompt

The request the original session was given, replayed verbatim.

It is not rewritten or summarised — the file that reaches the sandbox is the session’s own opening request, written to work/.req and piped into claude -p. A strategy may append to it under a heading, never edit it, so the baseline and the variant are answering the same question. Appending is itself a lever: the terse-context strategy adds one directive and changes nothing else.

Part 2

Strategy

A set of rules that says what one arm does differently. Two rule-sets exist, for two different jobs.

The tag comes from the parameters, not the label. A planner once proposed an arm it called “frontier, no compaction” when the baseline already had compaction off. Diffing the resolved parameters catches it: the arm is tagged no change, and its delta is reported as a noise floor rather than a finding.

Part 3

Baseline

A session that actually happened, replayed as the control arm.

The baseline is not a description of a task — it is a specific session on this machine, and it supplies three things the experiment cannot invent.

What it suppliesWhere it comes from
the requestthe session’s first user message
the working directoryevery file under its cwd, minus its own outputs, dotfiles, node_modules, tests/, and anything over 1 MB
the model tieropus → Opus 4.5, everything else → Sonnet 4.6 — so “the same job” means what it meant originally

Arms are compared against each other, never against the original session. A replay reaches an answer in five turns where the real session took seven hundred. “N× cheaper than the original” measures the replay’s incompleteness, not a saving.

Part 4

Operational settings

What stops a run from spending without limit, and what it costs to find out.

SettingDefaultWhat it bounds

There is a sixth limit that is not a flag: the ROI gate. A session whose best case saves less than the ~$1 of sandbox time needed to measure it is marked below gate before anything runs. On a real three-arm run the experiment cost $0.67; the session it measured had cost $0.22, and the hub said so.

Part 5

Verifier

Today it compares artifacts — the diffs, and nothing else.

On a real run this caught something a cost table cannot: the cheap arm failed to reject boolean input — isinstance(True, int) is True, so to_roman(True) returned "I" instead of raising — and committed a .pyc beside its tests. It came back 7.1× cheaper and 18 rubric points worse.

It compares artifacts, which is the current limit. An arm that produced no file is not scored at all — it reports an error rather than a cheap win — and a task whose value is in the conversation rather than the diff cannot be judged this way.

What the definition does not carry yet

Named here because an experiment definition with silent gaps is worse than one with stated ones.

repeatsEvery arm is n = 1. Agent variance makes a sub-15% single-run difference noise. Three repeats is the minimum before quoting a figure; repeats cost linearly.
thresholdsA strategy carries a gate sentence in prose — “judge score must not drop more than 1 point” — that nothing yet enforces. The gate runner is the next build item.
hidden suiteA replay has no tests it could not see. Rubric is the fallback, and a weaker signal than 52/69 — the report says which one it used.
gateway leversFour of the thirteen catalogued levers need something sitting in the request path — semantic cache, token rate limiting, response scoring, sanitising. They are defined, with their Kong plugin and parameters, and not yet runnable.
